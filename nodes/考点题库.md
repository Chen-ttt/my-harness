## A. 函数调用 /工具往返
### A1. ★一次完整的工具调用往返是什么流程?
user 发问 → 模型返回 `tool_calls` (此时是未完成轮次,它在等结果) → harness 执行工具 → 把结果作为 `tool` 消息喂回 → 模型基于结果给最终回答。消息顺序: `system → user → assistant(content+reasoning_content+tool_calls) → tool(role/tool_call_id/content 字符串)`。几个调用就追加几条 tool 消息。

### A2. ★回传时为什么要把整条 assistant 消息原样追加,而不是只塞 tool_calls?
带 `tool_calls` 的 assistant 轮次是未完成轮次,产生这些调用的思考(`reasoning_content`)属于这一轮。抽掉 → 模型「失忆了自己为什么调这个工具」,续写可能跑偏。所以整条原样回传最稳。补充:是否必须回传 `reasoning_content` 是厂商特定的——DeepSeek类不回传 400;实测 glm-5.3-flash 不要求。换模型要复查。

### A3. ★工具调用会以哪几种方式失败?分别怎么处理?
三种,各自回错误文本(不是抛异常):① 未知工具名(schema找不到);② `arguments` 非法 JSON(parse 阶段炸,每个 call 单独 try/catch,别带整批);③ parse 成功但缺必填字段(与②是两回事)。错误文本是模型的纠错信号,质量决定模型是修正还是瞎试 → 下一轮模型据此改工具名/参数。

### A4. ★工具执行失败为什么「返回文本」而不是「抛异常」?
未捕获的 Promise rejection 会杀进程 → 一次坏参数毁掉整个会话(state/token/结果全丢)。工具执行层是 harness 的故障隔离边界,契约=「永远 resolve 成 string,永不 reject」。错误码要有区分度(ENOENT/EISDIR/EACCES),模型才知道往哪个方向改。纵深防御:工具层 catch 已知错误,loop 层再兜兜底网的。

### A5.「幻觉工具调用」是什么?
模型编造不存在的工具名,或传格式错误/缺字段的参数。harness 必须对工具名和参数都做校验,失败回结构化错误文本让模型自我修正——而不是信任模型输出。

## B. 上下文 / token
### B1. ★为什么多轮对话里 token 越滚越大?增长量级?
LLM API 无状态,服务器两次请求间不记忆,`messages` 只活在你进程里。所谓多轮是幻觉——每轮把整部历史讲给一个失忆的模型。n 轮会话第1轮内容被重发 n 次…累计处理 token ≈ O(n²)。这是长会话又慢又贵的原因,也是上下文压缩/工具结果裁剪/跨会话 Memory 存在的根本理由。

### B2. ★抽掉 reasoning_content,丢的是什么、不丢的是什么?(裁剪判据)
工具结果是外部化的,作为独立 tool 消息常驻 messages,永远在;模型思考里的**「计划/中间推断」若没写进 content/tool_calls,一抽即失**。抽 `reasoning_content` 丢的是后者。这个区分就是「什么能裁、什么要留」的判据。

### B3.「没报错 ≠ 没影响」怎么理解?
硬失败(400,会尖叫)只是一种;还有软失败(不报错但回答质量/连贯性悄悄变差),更危险因为不吭声。评测若只看「有没有崩」就会漏掉软失败。

## C. 流式输出(SSE)
### C1. ★手写 SSE 解析有哪两个坑?
① `res.body` 吐字节(Uint8Array),须 `TextDecoder.decode(chunk, {stream:true})` ——多字节字符可能被切在 chunk 边界。② SSE 按行,但网络 chunk 不保证落在行边界:需 `buffer +=` 后切出完整行处理,半行留 buffer 等下一 chunk。`data:` 前缀、`data: [DONE]` 结束。

### C2. ★流式里 tool_calls 怎么拼?有哪两个 index?
两个 index: `choices[0].index` (第几个 choice,恒0) vs `delta.tool_calls[k].index` (第几个 tool_call,才是分组键)。拼接: `id / type / name` 取第一次出现(后续分片这些字段 undefined,不能覆盖);`arguments` 字符串片段按序 `+=`;用 index 定位而非 push(分片可能乱序到达)。

### C3. ★为什么「短参数下流式=非流式」不足以验收?
短参数时模型常一个 chunk 发完整个 tool_call,「追加」分支根本不执行,bug 潜伏。长参数被切片才暴露(比如把 id/name 覆盖成 undefined)。所以要构造会切片的长/乱序分片 case 测,不能只用短 case。

### C4. ★为什么把拼接抽成纯函数?
拼接是纯函数(deltas→结构),网络是 IO。焊一起 → 只能靠真实 API 测,而分片边界客户端控制不了、还 flaky。拆开 → 纯逻辑 fixture 确定性测,IO 用假 stream 单独测。判断信号:「只能靠真实外部系统才能测」= 逻辑和 IO 焊死了。

### C5. ★流式函数该 return 什么形状?
和非流式等价的形状(tool_call 还原成 `{id, type, function:{name,arguments}}`)、arguments 保持未解析字符串,让下游分发逻辑零改动——传输细节(流/非流)不该泄漏到上层。错误处理(坏 JSON parse)单一归属于下游,别在流式层提前 parse。

## D. workflow vs agent
### D1. ★workflow 和 agent 的本质区别?判据?
本质:控制流在谁手里——人预先编排(workflow)vs模型运行时动态决策(agent)。判据不是任务名字,是**「输入方差 + 一条固定流程能否服务所有输入」**。同一任务可以是 workflow 也可以是 agent。

### D2. ★agent 的代价是什么?默认该选哪个?
agent 的轮数由模型运行时决定 → 不可预测(2轮还是 20 轮)→ token/耗时飘、难调试难复现(还有 O(n²) 上下文)。默认「能 workflow 就别 agent」,用灵活性换代价值得。

### D3. 增强型 LLM、编排者-执行者 各是什么?
增强型 LLM(augmented LLM)=LLM+检索/工具/记忆,一切 workflow/agent 的最小积木。编排者-执行者(orchestrator-workers)=一种 workflow 模式,一个 LLM 拆任务分给多个 worker、再汇总。

### D4. ★(案例)把一个「现状调研」skill 从固定流程改成让模型自己决定看什么,好不好?
取决于输入方差:若需求长得都差不多,固定流程稳定便宜可复现,workflow 更优;若输入五花八门、固定流程要么浪费要么漏,则给模型「业务域地图+工具+映射」让它自适应(agent)覆盖更好,代价是轮数不可预测/更费 token。哪个更好用 benchmark A/B 跑——设计问题最终落回评测。

## E. 工具安全 /沙箱(阶段1已实践)

### E1. ★Prompt Injection 有哪几种?完整攻击链路是什么?
直接注入(用户输入带指令)vs 间接注入(网页/文档/工具结果/RAG 内容里夹带指令,最危险:读文件是正常操作,恶意文本不知不觉进上下文)vs Jailbreak(绕模型自身安全策略,不是注入但常混问)。完整链路:仓库 README 埋指令 → 模型读文件(正常操作)→ 恶意文本进上下文 → 模型「尽职」调用工具 → 私钥外泄。根因:LLM 无法像编译器区分代码与数据那样区分指令与外部数据(Context Mixing)。注意:只读工具也要拦——目录结构、错误码差异(ENOENT vs EISDIR)本身就是情报。

### E2. ★为什么不能靠 system prompt 约束模型?「模型不是安全主体」怎么讲?
prompt 遵循是概率行为(上下文膨胀、注入都会降低遵循率);代码检查是确定性行为。「请勿访问敏感路径」写在 system prompt 是请求,写在 path.resolve 检查里才是边界。口试金句:「模型可以提议,但不能自行决定权限」。推广:安全属性必须做成确定性用例,不能做成统计用例。

### E3. ★路径安全有哪三个攻击入口?
① 前缀绕过:/proj-secret 以 /proj 开头,startsWith 误放行 → 比较必须用 startsWith(root + path.sep)(即 /proj/),且单独放行 resolved === root(模型传 "." 时 resolve 结果就是 root,列目录是合法操作)。② 绝对路径:path.resolve(root, p) 遇绝对路径 p 会直接采用 p、忽略 root——resolve 不会自动把你锁在 root 内,词法门必须检查 resolve 的结果,不能信任「root + 用户输入」一定落在 root 里。③ 符号链接:path.resolve 是纯字符串运算,fs 才物理跟随链接 → 词法门挡不住「传送门」(实验证据:guard 看到的和 fs 打开的不是同一条路径)。

### E4. ★guard 的正确形状:为什么两道检查必须串联(AND)?
第一道·词法(纯字符串,零 I/O):拦明显越界,必须放前面(越界路径不该被报成 ENOENT,还省一次磁盘 I/O)。第二道·realpath(读磁盘):展开符号链接再查一次边界。必须 AND 串联(任一否决即拦截):|| 并联 = 第一道放行就整体放行,且短路求值让第二道根本不执行(实操踩过)。单点收口:安全检查集中在 guard.mjs 一处,散落各工具 = 忘一个漏一个。顺序不可换:realpath 在前会让越界路径报 ENOENT(语义撒谎 + 安全退化)。

### E5. ★guard 三个错误分支的语义决策是什么?
ENOENT(不存在)→ 放行词法路径:链接攻击需目标真实存在才成立,故不开洞;「不存在」由 fs 去报才诚实(拼写错 ≠ 越界,模型纠错方向才对)。EACCES 等(查不了)→ throw(fail closed):无法证明合法就拒绝,绝不默认放行。成功 → 返回 realpath 展开后的路径而非词法路径:缩小 TOCTOU 窗口。附带:错误消息最小泄露——不透露 root 外真实路径(错误消息也是攻击面),只回显模型自己传的参数。

### E6. 什么是 TOCTOU?我们的取舍是什么?
Time-of-Check to Time-of-Use:检查和使用之间链接被替换的竞态。取舍:返回已展开的真实路径,后续 fs 不再跟随链接,竞态窗口压缩到两次调用之间;残余风险明确接受(彻底修复需 openat/dirfd,业界普遍也这么取舍)。考点:知道自己在接受什么、能讲清残余风险,而不是假装没有。

### E7. 沙箱有哪几个层级?各解决什么?
最小形态:文件系统只读白名单(workspace root)——阶段 1 已做。业界完整:写隔离、shell/进程隔离、网络出口管控、容器/微 VM。单一隔离不够,必须组合(纵深防御)。权限系统(高风险操作人工审批)是另一条线,Claude Code 等真实 harness 均内置——阶段 2 会做。

## F. 测试与工程素养(阶段 1 方法论 + 阶段 2 Code Review 沉淀)

### F1. ★什么是「断言来自规格,不是实现」?
反例:写实现时顺手把断言写成和实现一致(如断言返回 SUCCESS 字面量、把「越界报 ENOENT」迁就成断言)→ 测试绿了但没保护任何东西。正确:先定规格(应该是什么),实现去够规格;规格不动,实现动。实操两次踩过:断言迁就实现 = 测试形同虚设。

### F2. ★漏洞如何转成回归测试?
步骤:先把攻击路径写成测试(断言「能读到私钥」)→ 修复 → 反转断言(断言「报越界」)→ 永久看守(test-tool.mjs 实验 9 看守符号链接洞)。效果:谁改坏 guard,这条测试第一个红。价值:漏洞修复不是终点,防回归才是。

### F3. fixture 自建自清是什么意思?
fixture = 测试的前置环境(临时目录、符号链接等)。自建:测试自己创建所需环境,不绑架外部环境;自清:try/finally 里删除,断言炸了环境也必清,不残留垃圾。否则测试之间互相干扰、flaky。

### F4. 测试为什么不能依赖启动姿势?
Node 相对路径按启动目录(process.cwd())解析 → 换个目录启动,同一脚本的 ../x 指向不同地方 → flaky。对策:用 import.meta.dirname 锁定模块自身所在目录。一般化:flaky test 的经典来源就是环境依赖(启动目录、全局状态、网络)。

### F5. ★什么是弱断言?它的危害?
只验证「会停」不验证「停的原因可区分」(`assert.notStrictEqual(stopReason, "stop")`)。症状:测试绿了,但没保护住你真正在意的性质。本次实例:`http_error` 和 `abnormal:sensitive` 都被塞进 `other_error`,测试绿掉——而 stopReason 正是阶段4 Trace 的主分组维度,合并后看板上 `Other_error 98次` 等于零信息。

### F6.「测试即规格」怎么理解?
本次真实经历:先不知道 `stopReason` 该有哪些值,读测试代码(七个出口各断言什么)才搞清契约,再回去补实现。清单 = 状态机出口的规格说明。所以测试的第一价值不是防回归,是逼你把契约定下来。

### F7. ★为什么「只能靠真实外部系统才能测」是个坏信号?
说明逻辑和 IO 焊死了。Loop 的决策逻辑(分派/计数/退出)是纯逻辑,发 HTTP 是 IO。把 `callLLM / runTool / sleep` 改成注入的参数,就能用脚本化假响应确定性地测:429耗尽、maxRounds触发、异常 finish_reason——不花钱、不联网、不等15秒(`sleep`也注入成空函数)。

## G. Agent Loop(阶段2)
### G1. ★Loop 怎么按 finish_reason 分派?
三类:①继续下一轮= `tool_calls`(执行工具 → push 结果 → 回到顶部),这是 Loop 之所以是 Loop 的主力场景;②正常结束= `stop`;③异常结束= `length`、`model_context_window_exceeded`、`sensitive`、`network_error`,以及未知值。注意:③里几种的恢复策略不同(length/context该压缩后重试=阶段3;sensitive该告知用户),第一流统一「识别+终止」,但 stopReason 要保留粒度,别合并成一个桶。

### G2. ★为什么必须设最大轮数?到顶了该返回什么?
模型会原地打转:调研任务里资料提到一个不存在的仓库,模型反复换工具/换路径重试,永不收敛。最大轮数是硬上限(到顶无条件退出)。「再发一次请求让模型总结进度」是软策略,必须放在上限之内(如剩最后1-2轮时提示收敛)——放在上限之后等于「保险丝后面又接了根电线」,那一次请求本身也会再触发工具调用/超时。

### G3. ★★计数器 ≠ 限制(本次亲手踩的死循环)
`retryRounds += 1` 加了,但全文没人读它 → 持续429时它数到10万还在数,死循环一行没少。**限制 = 计数 + 判断 + 到达后的动作**,三者缺一,前面的都是装饰。

### G4. ★为什么需要两级计数器?
两件不同的事:① Loop 轮数=模型思考了几步;② 单次请求的重试次数=网络抖动。重试不该消耗「思考步数」预算(网络失败不是 LLM 执行任务的成本),但也不能无限进行,所以要各自的上限。本项目取会话级总重试预算(每轮不归零):网络整体不稳就及早放弃。另一种是单请求预算(每轮归零),代价是 20 轮 ×3 次可能总耗时夸张。语义不同,面试要能说出取舍。

### G5. ★continue 重试时有什么陷阱?
`continue` 把控制流送回循环顶部,但不会把你改过的状态送回去。现在重试点干净,只因为 `callLLM` 抛异常时这一轮还没执行到任何 `push`——这是当前语句顺序的副产品,不是被保证的不变量。反例:若将来做「整轮重试」(工具执行到一半失败),`msgList` 里已躺着 assistant + 部分 tool 消息,`continue` 后重复 push → 消息结构非法 → 400。对策:重试关在不碰 `msgList` 的函数里,让它物理上没能污染状态;至少写下这条不变量。

### G6. ★哪些错误重试有救,哪些白搭?
429(限流)、5xx(服务端临时故障)→ 重试有意义(生产上用指数退避 + 抖动,不是固定3s)。4xx 尤其400(请求本身非法,如 messages 结构错)→ 重试多少次都是同样的400,必须立即放弃。前提:底层必须把 `status` 传上来。本次踩坑: `new Error(msg, statusText)` 第二个参数不是拼进消息的,只认 `{ cause }`,写错等于把判据在源头掐断——最底层丢信息,会掐死上层的决策能力。包装错误用 `{ cause: e }`,别手工摘 `e.message`(DNS失败的真实原因在 `e.cause`,堆栈也会丢)。

### G7. ★为什么 callLLM 不该 process.exit ?
职责错位:「发一个 HTTP 请求」的函数没有资格决定整个程序的生死。重试/降级/终止是策略决策,属于 Loop 这一层;callLLM 只负责「成功返回结果,失败如实抛出」。具体代价:`exit` 会跳过 token 汇总等收尾逻辑;且任何重试机制都形同虚设(一次失败整个进程就没了)。用 `break / return` 而不是 `exit`。

### G8. ★★为什么 Loop 必须返回结构化结果,而不是 console.log ?
`console.log` 不可断言、不可被上层消费。返回 `{ stopReason, rounds, retries, totalPromptTokens, ... }` 后:测试能断言、监控能接、Trace 能落库。这是「可观测」的起点。配套:只打 token 总和会丢掉按轮次的分布,而「第2轮 prompt 比第1轮大多少」才是定位 O(n²) 的数据——总和只能告诉你贵,不能告诉你哪里贵(阶段4的 Span 雏形)。

### G9. ★计数器的命名陷阱(off-by-one)
`requestRounds = 1` 起始、成功后 `+=1` → 它存的是「下一轮的编号」,但名字听起来像「数量」,于是跑2轮返回3。要么存数量(`rounds = 0`,成功后 `++`,闸门 `>= max`),要么存序号(叫 `roundNo`,返回时 `-1`)。名字必须说出它数的是什么。

### G10. ★保护机制失效时要响亮失败,不能静默放行
把 `maxRounds = 5` 的默认值删掉后:调用方忘传 → `rounds > undefined` 恒为 `false` → 那道闸门永远不触发,无限重试原地复活,而且不报错、不告警,只在生产上无限跑。默认值不是为调用方省事,是保护机制的兜底;更狠可在入口显式校验 `if (!(maxRounds > 0)) throw`。同类:错误处理里 `e.cause.status` 在 cause 为 undefined 时直接 TypeError 崩溃(用 `?.`)——错误分支是最少被执行的、因此最少被验证的代码。

### G11. ★「让非法状态无法表示」——以及它的边界
把「设 stopReason」和「退出」合成一个动作(`return finish(reason)` 取代 `break + 共享可变变量`)。诚实的边界:纯 JS 里这不是强制的(可以写 `return finish()`),真要咬住得靠类型系统(TS把返回类型定成必含 stopReason 的联合类型)。它真正买到的是:消除跨迭代存活的可变变量。本次实例——max_rounds 出口漏设 stopReason,返回的不是 `undefined`(一眼看出坏了),而是上一轮残留的 `'tool_calls'`(错但看起来完全合理,会把排查带到假线索上)。这和 G10 是同一个病:该响亮失败的地方安静放行了。

## H. Multi-Agent 编排(了解级:4 家 JD 点名,能答核心即可)

### H1. ★Multi-Agent 常见编排模式有哪些?
顺序流水线(prompt chaining):A 输出喂 B,固定工序(翻译→校对)。并行扇出(parallelization):同任务分发多个 agent 并行,再汇总/投票。路由(router):入口先意图识别,分发给专门 agent——小红书 JD 的「意图路由」。编排者-执行者(orchestrator-workers):一个 LLM 拆子任务分给 worker、再汇总(呼应 D3)。网络式(自主协作):agent 间自由对话,最难控制。选型判据与 workflow vs agent 一致:任务能否明确分解、是否需要不同专长/上下文隔离。

### H2. ★Multi-Agent 之间怎么通信与共享状态?
消息传递:结构化消息(任务 + 上下文切片)发给子 agent,结果返回主 agent。共享状态:白板/共享 Memory/消息总线,多 agent 读写需并发控制。SuperAgent 路由编排(小红书企业级 JD 原话):主 agent 负责任务分发、消息传递与结果汇总。面试点:子 agent 上下文给多少、怎么切,错误如何跨 agent 传播。

### H3. ★什么时候该上 Multi-Agent?代价是什么?
何时:任务可分解为不同专长子任务;单 agent 上下文/工具爆炸;需要并行加速。代价:编排与通信开销、错误跨 agent 传播放大、端到端难调试难复现、token/成本上升。默认:能单 agent + 工具解决就别 multi;拆的理由是「职责单一 + 上下文隔离」,不是听起来高级。

## I. 稳定性与降级(了解级,阶段 5 会扩展)

### I1. ★熔断、降级、限流有什么区别?(小红书 JD「熔断降级」,高频混淆)
限流:入口控流量,超阈值直接拒绝(管「来多少」)。降级:故障时砍功能保核心,返回兜底/缓存结果,有损但可用(管「给什么」)。熔断:依赖连续失败到阈值 → 暂时不再调用(快速失败)→ 过段时间半开放探测 → 恢复则闭合,否则继续断(管「还调不调用」)。三者常组合:熔断打开期间配合降级给兜底响应。类比:景区限流 / 手机低电量关动画 / 保险丝跳闸。


### 2026-10-23：环境配置与输出

- Q：为什么 `.env` 不提交而 `.env.example` 可以提交？
  A：前者保存本地真实凭据，后者只保留变量名和占位值；忽略规则不能隐藏已提交源码中的密钥。Node 可通过 `--env-file=.env` 加载配置，代码仍从 `process.env` 读取。
- Q：为什么函数返回了结果，终端仍可能无输出？
  A：return 将值交给调用方，打印需要显式调用 console.log 或 console.dir；本次用户补日志后确认可见结果。


### 2026-10-24：工具参数校验与测试边界

- Q：为什么不能用 !params[key] 判断缺字段？
  A：0、false、空字符串也是假值；用 Object.hasOwn 判断自身字段存在，再按契约检查类型。
- Q：JSON.parse 成功代表参数是对象吗？
  A：不代表；顶层 null、数组和基本类型也可能解析成功，需独立检查形状，解析 catch 只包解析步骤。
- Q：为何提取 validateParams？
  A：业务与测试复用实现，导入校验模块不会启动 ask.mjs 顶层的 Key 检查和 Loop。当前接口接收整个内部 toolDefinition，模型参数需运行时校验。
- Q：九条校验测试能证明工具调用正常吗？
  A：不能；入口可能提前误拒绝调用。需增加调用层测试，验证合法参数调用工具、非法参数不调用工具。测试应能发现保护逻辑被删除或改错。

- Q：如何避免工具定义与实现漂移，以及注册名 toString 被误判重复？
  A：从同一注册表生成模型 tools 和内部 toolImpls；写入前用 Object.hasOwn(acc, name) 检查自身属性。acc[name] 会读到继承属性，不能用其真假判断是否已经注册。

- Q：stopReason 与 errorDetail.kind 有何区别？
  A：前者描述执行为何结束，后者描述原始错误类别。例如重试耗尽是 retry_exhausted，原始错误仍为 http，status 为 429。终止错误详情只在确定终止时赋值，429 重试成功应为 null；程序按 kind 分类，不匹配错误文案。

- Q：AbortController 为什么按请求创建？
  A：signal 被取消后不会恢复；每次请求独立创建以隔离生命周期。abort 是通知，底层必须配合。当前 fetch 接收 signal，Loop 计时并优先识别超时，finally 在错误处理与退避前清理计时器。当前超时直接结束任务，不自动重试；本地取消不保证服务端停止。

### 2026-10-25：取消通知与总预算（请求与退避测试已通过，工具取消待做）

- Q：AbortController 和 AbortSignal 分别负责什么？
  A：controller 发出取消通知，signal 交给操作接收；abort(reason) 设置取消状态与原因，不会自动退出 Loop 或强制终止任意 Promise。
- Q：AbortSignal.any 如何组合任务超时和请求超时？
  A：任意输入取消即取消合成 signal，其 reason 保留最先触发的来源；不会反向取消其他输入。它只组合通知，不创建预算计时器。
- Q：总预算与单次请求预算的计时器在哪里创建和清理？
  A：总预算在循环前创建，在任务 finally 清理；请求预算按请求创建和清理，不能把总预算每轮重置。
- Q：为什么只把总预算 signal 传给 fetch 不够？
  A：退避和工具也可能正在等待；它们必须实际响应取消。Promise 版 setTimeout 可接收 signal，取消后拒绝；捕获后应退出，不能继续重试。
- Q：捕获的异常一定等于 signal.reason 吗？
  A：不一定，取决于 API；例如 Promise 版计时器以 AbortError 拒绝。区分取消来源应读取相关 signal 的 reason，同时保留普通错误的处理。
- Q：throwIfAborted 能替代等待中的取消吗？
  A：不能，它只检查调用时的状态；用于阻止取消后的后续工作，等待本身仍需要支持 signal。

完整示例与来源见[取消与总时间预算笔记](学习笔记2026-10-25-取消与总时间预算.md)。

- Q：catch 内 await 退避抛出的取消异常，会被同一个 catch 捕获吗？
  A：不会；需要为该等待增加处理或由外层捕获，否则 runLoop 拒绝而非返回结构化结束结果。本次总预算测试已复现。
- Q：为什么循环后的 clearTimeout 不足以保证清理？
  A：异常会直接跳过循环后的代码；任务级 finally 才能覆盖异常退出。本次用工具抛错后 signal 仍被计时器取消复现。
- Q：替换为可取消 sleep 时，为什么不能绕过原来的注入参数？
  A：会让测试替身及其中的断言失效，并产生真实退避等待；应让默认实现和注入调用共同支持取消参数，而不是留下无人使用的 sleep 接口。

- Q：abort 后，finally 和请求成功计数还会执行吗？
  A：abort 本身只发通知；若 await 的请求响应取消并拒绝，先执行内层 finally，再进入外层 catch，跳过成功计数。若操作忽略 signal，则不能保证 await 结束。
- Q：整个任务包 try/finally 是滥用错误处理吗？
  A：不是；finally 按资源生命周期清理，并不吞掉异常。catch 才决定错误处理策略；未识别错误应向上传播，不能静默继续。
- Q：sleep(ms, signal) 与 Node 的 setTimeout(ms, value, { signal }) 有什么区别？
  A：前者是自己约定的包装函数接口，后者是底层 API 接口。包装函数内部已把 signal 包进 options，调用包装函数时不能再多包一层。

- Q：工具已有取消 catch，为什么还检查 await 前后的取消状态？
  A：catch 仅处理抛异常的路径；工具可能忽略取消后正常返回。调用前检查阻止启动已取消的任务，调用后检查阻止迟到结果继续驱动后续工具或模型。检查不能提前终止忽略 signal 的操作。
- Q：工具循环中 break 能终止整个任务吗？
  A：break 只退出最近一层循环；当前结构还需设置 stopFlag 和 task_timeout，外层 while 才会停止。throwIfAborted 放在相应 try 内可复用统一取消分支。

- Q：readFile 支持 signal，能推断 readdir 也支持吗？
  A：不能。当前 Node v24 的 readdir 没有 signal 选项，本地已取消 signal 实验仍正常返回。传参不报错不代表功能生效；readdir 只能靠前后检查拒绝继续工作，不能借此打断正在等待的目录读取。
