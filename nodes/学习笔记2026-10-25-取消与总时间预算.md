# AbortController、AbortSignal.any 与总时间预算

日期：2026-10-25。阶段 A「最小可靠运行时」，属于必须动手的异步与取消机制。

状态：请求与退避总预算、工具取消控制流及真实文件读取取消已验证，工具取消模块口述通过。目录读取仅支持前后检查，不能中断等待。本文示例用于说明 API；项目验证证据见学习历史 2026-10-25 各轮记录。

## 1. 先区分发通知的人和接通知的对象

`AbortController` 用来发出取消通知；它的 `signal` 是交给操作接收的通知对象。调用 `abort()` 不会自动退出 Loop，也不会强制终止任意 Promise。

| API | 用途 |
| --- | --- |
| `new AbortController()` | 创建一组 controller 与 signal |
| `controller.signal` | 传给支持取消的操作 |
| `controller.abort(reason)` | 发出取消通知，可附带原因 |
| `signal.aborted` | 是否已经取消，初始为 false |
| `signal.reason` | 取消原因；未取消时为 undefined |
| `signal.throwIfAborted()` | 已取消则抛出 reason，否则继续 |

```js
const controller = new AbortController();
const reason = new Error("task_timeout");

controller.abort(reason);
console.log(controller.signal.aborted);          // true
console.log(controller.signal.reason === reason); // true
```

signal 一旦取消不能复位，所以每次新请求需要独立的请求级 controller。不给 `abort()` 传原因时，默认原因是名为 `AbortError` 的 DOMException。

## 2. AbortSignal.any：任意一个取消即可

```js
const taskController = new AbortController();
const requestController = new AbortController();
const signal = AbortSignal.any([
  taskController.signal,
  requestController.signal,
]);

requestController.abort(new Error("request_timeout"));
console.log(signal.aborted);       // true
console.log(signal.reason.message); // request_timeout
console.log(taskController.signal.aborted); // false
```

合成 signal 接收输入的取消；它不会反过来取消其他输入 controller。合成后的原因由首先触发取消的输入决定，后续取消不会覆盖它。如果传入时已有 signal 取消，结果会立即处于取消状态；多个输入已取消时，采用输入顺序中第一个已取消者的原因。

`AbortSignal.any` 在 Node.js v18.17.0 / v20.3.0 加入。使用前确认运行版本支持。

请求接线示意（`url`、`options` 来自调用方，此片段不是完整程序）：

```js
await fetch(url, { ...options, signal });
```

合并信号本身不负责计时；计时器仍需分别创建和清理。

## 3. 两种预算的生命周期

| 范围 | 创建 | 清理 |
| --- | --- | --- |
| 整个任务 | 进入 Loop 前一次性创建 | 整个任务的 finally |
| 单次请求 | 每次请求开始时创建 | 本次请求的 finally，退避前清理 |

总预算覆盖模型调用、退避、工具执行。每轮重新计时会重置预算，失去累计限制。

已正确回答的例子：总预算 10 秒、请求超时 6 秒。请求在第 7 秒开始，则总预算在第 10 秒先触发；请求在第 2 秒开始，则单次请求在第 8 秒先触发。这里假设请求一直未返回，且事件循环正常调度。

只在轮次开头检查可以阻止部分后续操作，但不能唤醒正在等待的操作。采用到期取消策略时，应同时让等待响应 signal，并在启动后续操作前检查取消状态。

## 4. 退避也需要接收取消

下面是可独立理解的用法示例，未在本次归档中执行：

```js
import { setTimeout as sleep } from "node:timers/promises";

const controller = new AbortController();
const timer = setTimeout(() => {
  controller.abort(new Error("task_timeout"));
}, 100);

try {
  await sleep(400, undefined, { signal: controller.signal });
  controller.signal.throwIfAborted();
  console.log("准备重试");
} catch (error) {
  if (error.name === "AbortError" && controller.signal.aborted) {
    console.log(controller.signal.reason.message);
  } else {
    throw error;
  }
} finally {
  clearTimeout(timer);
}
```

`sleep` 的第二个参数是正常完成时返回的值，第三个参数才是 options。全局 `setTimeout` 用来安排取消；导入的 Promise 版用来等待，别混淆。

预期约 100ms 后进入取消分支，不打印“准备重试”。Promise 版计时器取消时以 AbortError 拒绝；捕获的异常不应一律假设等于传给 `abort(reason)` 的对象。取消来源从相关 signal 的 reason 读取，普通失败应继续保留。

## 5. 工程边界和当前任务

- 只传给 fetch 不能取消退避或工具；每个等待点都要实际支持并响应取消。工具取消是下一步。
- 取消通知不等于退出循环；异常处理分支必须结束任务，不能继续重试。
- `throwIfAborted()` 只检查当前状态，不能替代等待中的取消支持。
- 合成 signal 的 reason 可保留最先触发的来源；稍后检查两个原始 signal 时，它们可能都已取消，不能随意按检查顺序猜来源。
- 本文用 Error.message 展示原因；项目按既有结构化错误契约分类，不应依赖面向人的错误文案。
- 取消不保证撤销已发生的副作用，也不保证远端停止计费；同步阻塞和忽略 signal 的操作不会因此被强制停止。计时器也不保证精确时刻触发。

当前实现范围：总预算接入请求、退避和工具链，区分任务到期和单次请求超时；readFile 支持读取期间取消，readdir 与路径解析只能在等待前后检查。相关回归已通过，不能据此宣称整个任务已有严格时间上限。下一模块为 Token 预算。
