# 学习笔记2026-10-13:函数调用完整往返·流式·workflow vs agent(阶段1收官)

今日一句话
把单次请求打磨成「完整工具调用往返+流式接收」,并在workflow/agent的判据上想透了一个真实案例。阶段1归档,三道验收题全过。

## 一、函数调用完整往返(核心,必须脱稿讲)

### 1.消息往返的形状 ★★★

- 流程: user →模型回 tool_calls (未完成的轮次,它在等结果)→执行工具 →把结果喂回 →模型基于结果给最终回答。
- 回传时整条 assistant 消息原样追加(含 content / reasoning_content / tool_calls),再逐个tool_call追加一条tool消息( { role:"tool", tool_call_id, content: } )。几个调用就几条tool消息。
- 为什么整条原样:带tool_calls的assistant轮次是未完成轮次,产生这些调用的思考(reasoning_content)属于这一轮。抽掉 →模型「失忆了自己为什么去调这个工具」。
详见下方 reasoning_content 实测。

### 2.三种工具调用失败,各自回错误文本(幻觉调用处理)★★★

- 未知工具名(schema里找不到)→错误文本
- arguments 非法JSON( JSON.parse 阶段炸)→每个tool_call单独 try/catch,哪个坏回哪个,别一个坏参数带崩整批
- parse成功但缺必填字段(与「JSON残缺」是两回事)→错误文本
- 错误文本是模型的纠错信号:下一轮模型据此改工具名/改参数。实测三种都能让模型自我修正。

### 3.无状态与 O(n²)(Context Engineering 的根)★★★

- LLM API无状态:服务器两次请求间什么都不记得,msgList 只活在你进程里。所谓「多轮对话」是幻觉——每轮把整部历史讲给一个失忆的模型。
- 增长不是线性:n轮会话,第1轮内容被重发n次…累计处理 token ≈ O(n²)。这是长会话又慢又贵的原因,也是「上下文压缩/工具结果裁剪/跨会话 Memory」存在的全部理由。
- 第二次请求 prompt_tokens 明显变大,主因=工具结果被注入上下文。设想 read_file 读5000行 →下轮请求爆炸,这就是「工具结果裁剪」要解决的(阶段3)。

### 4. reasoning_content回传:实测 > 文档 ★★★

- 实测 glm-5.3-flash 不硬性要求回传(抽掉3次均不报400、正常返回)。DeepSeek 的「must be passed back / 400」是厂商特定行为,勿跨模型照搬。
- 「没报错 ≠ 没影响」:只验证了硬失败(400尖叫)。软失败(不报错但质量悄悄变差)没测——因为任务太简单(list_dir 结果即可独立回答),模型不需要回看思考。软失败更危险:不吭声。
- 裁剪判据(关键区分):工具结果是外部化的、作为独立tool消息常驻,永远在;模型思考里的「计划/中间推断」若没写进 content/tool_calls,一抽即失。抽 reasoning_content 丢的是后者,不是工具结果。
- 工程决策要点:就算模型不要,该不该主动留是压缩取舍(连贯性 vs token)。有意丢要写注释标明假设(换模型可能崩),否则「有意丢」和「顺手丢」在代码上无从区分。

## 二、流式输出(SSE手写解析)(核心,必须能写)

### 1.字节与解码 ★★★

- res.body (fetch)吐的是字节 Uint8Array,不是字符串,须 new TextDecoder().decode(chunk, { stream: true })。{ stream:true } 关键:多字节字符(汉字)可能被切在 chunk 边界,带上它才能跨 chunk 正确拼。

### 2.行缓冲(buffer)★★★

- SSE按行( data: {...} , data: [DONE] 结束),但网络 chunk 边界不保证落在行边界:一个 data: 行可能被切成两 chunk,或一个 chunk 含多行。
- 解法: buffer += 解码文本,然后循环 indexOf("\n") 切出完整行处理,最后半行留在 buffer 等下一 chunk。只 += 不切 = 没解析。

### 3. tool_calls分片拼接(本节最难)★★★

- 两个index要分清: choices[0].index (第几个choice,单响应恒0)vs delta.tool_calls[k].index (第几个tool_call,才是分组键)。
- 拼接规则: id / type / name 取第一次出现(后续分片这些字段是 undefined,不能覆盖已有值); arguments 是被切开的字符串片段,按序 += ( || "" 兜底 undefined)。
- 用 index 定位,不用 push:分片不保证按序到达,乱序时 push 会串位。
- 典型潜伏 bug:短参数时 GLM 一个 chunk 就发完整 tool_call,"追加"分支根本不执行 →短 case 下流式/非流式看起来一样,长参数被切片才暴露。流式 不能只用短 case,要构造会切片的长/乱序分片。

### 4.纯逻辑 / IO 分离(harness工程通用方法论)★★★

- 拼接是纯函数(deltas →结构, stream.js::mergeToolCallDeltas ),网络读流是IO。
- 焊一起 →只能靠真实API测;而分片边界客户端控制不了、还 flaky。拆开 →纯逻辑喂 fixture 确定性测(手工造三片/乱序分片),IO用假 stream 单独测。
- 判断信号:「只能靠真实外部系统才能测」的代码,往往就是逻辑和 IO 焊死了——拆。

### 5.接口抽象:传输细节不泄漏到上层 ★★☆

- 流式函数 return 一个和非流式等价的形状( { choices:[{ finish_reason, message:{ role, content, reasoning_content, tool_calls }}], usage } ),其中tool_call还原成 { id, type, function:{ name, arguments } }。arguments 保持未解析字符串。
- 效果:下游「分发工具 + 往返」逻辑零改动。换流/非流只是「换根水管」,上层不该知道换了。
- 填空3的判断(不在流式层 parse args)是对的:错误处理要单一归属,坏JSON留给下游已有的 try/catch,别散两处。

## 三、workflow vs agent(核心,高频考点)★★★

### 1.核心判据

- 一刀:控制流在谁手里——人预先编排 vs 模型运行时动态决策。
- 判据不是任务名字,是「输入方差 + 一条固定流程能否服务所有输入」。同一任务(现状调研)可以是 workflow 也可以是 agent。
- 代价这一半(别只说"能不能"):agent的轮数由模型运行时决定 →不可预测(2轮还是20轮)→token/耗时飘、难调试难复现。默认「能 workflow 就别 agent」,用灵活性换代价值得。

### 2.两个积木/模式(复述补漏)

- 增强型 LLM(augmented LLM):LLM + 检索/工具/记忆,是一切 workflow/agent 的最小积木。
- 编排者-执行者(orchestrator-workers):一种 workflow 模式,一个 LLM 拆任务分给多个 worker、再汇总。

### 3.真实案例:大佬把「现状调研」去流程化

- 原版 workflow:硬编码「先知知识库后代码库」。
- 大佬改版 agent:只留工具清单 + 架构介绍 + 业务域 + 域⇨库映射(=增强型 LLM 的上下文装备),流程交给模型按用户输入自适应决定看什么。
- 本质:判断「现状调研的输入方差大到固定流程 hold 不住」(固定流程对很多输入要么浪费要么漏),于是用 agent 换覆盖面,代价=轮数不可预测/更费 token。
- 哪个更好?用 benchmark A/B 一跑,比通过率/覆盖率/token/稳定性。→设计问题最后落回评测(JD 把 Agent 理解"和"评测绑一起的原因)。

## 四、评测设计(方法确立,完整实践 defer 阶段4)

严谨评测的要件(本次确立,阶段4用真实场景落地):

- rubric / gold answer 先写死(否则拍脑袋、不可复现)——这就是本职 LLM-as-Judge。
- 对照:同题同提示,只变 reasoning_effort。
- 重复:每档跑 N 次(LLM 有随机性,量起来结果才可信)。
- 判定规则跑前定死(如"low 通过率落在 max 波动内且 token 明显更低则 low 胜"),否则跑完会事后找理由=结论先于证据。
- harness 专属风险:别只测问答质量,要专测「低 reasoning 会不会损工具调用」(漏调/调错/参数质量)。
- 微验证已做:low 在当前简单多工具任务上无工具调用退化(n=3)。注意外推陷阱:只覆盖简单任务,"任务都简单不会有差异"是把结论外推到未测范围。
