## 技术备忘（历史记录，适用条件待逐项校准）

> 保留当时的学习结论，不代表所有模型/协议通用。模型参数、finish_reason、reasoning_content 等需按具体厂商与版本核对；O(n²) 结论需注明历史重发和每轮增量假设；路径 guard 不等同完整隔离。下方 process.exit 设计债已在上方 2026-10-14 记录完成，保留原文仅供回溯。

- `finish_reason` 共 6 种:stop、tool_calls、length、sensitive、network_error、model_context_window_exceeded。length 不能当成功:推理模型的思考计入 max_tokens,额度太小会 content 为空而 HTTP 仍是 200。
- `tool_calls` 是数组,路径为 `.function.name`、`.function.arguments`、`.id`。arguments 是字符串,需 `JSON.parse`,且模型生成的参数不可信,必须校验。
- 消息顺序(已对照文档示例):system → user → assistant(content + reasoning_content + tool_calls) → tool(role / tool_call_id / content 字符串)。有几个调用就追加几条 tool 消息(示例只处理了第一个,不能照抄)。开启思考并使用工具时须保留并回传 reasoning_content,最稳做法是整条 assistant 消息原样追加。
- 网络层失败(如 DNS)时 fetch 抛异常,真实原因在 `e.cause`;4xx/5xx 靠 `res.ok` 判断。
- 单次 token 用量波动大,任何结论都要来自多次运行。
- 路径安全已实测销账:`path.resolve` 是纯字符串运算,fs 才物理跟随符号链接;guard(`tools/guard.mjs`)词法+realpath 双门串联,防前缀绕过与符号链接。错误分支语义与取舍见 `nodes/学习笔记2026-10-10:工具层与路径安全.md`
- 测试规范实操确立:断言来自规格、fixture 自建自清、漏洞反转成回归测试(细节见 notes)
- 文档称 reasoning_content 仅限 4.5 系列,实测 glm-5.3-flash 也返回,以实测为准。
- reasoning_content 回传:实测 glm-5.3-flash 不硬性要求回传(抽掉 3 次均不报 400,正常返回),DeepSeek 的「must be passed back / 400」是厂商特定行为,勿跨模型照搬。注意:本实验任务太简单(list_dir 结果即可独立回答),只验证了硬失败(400),未验证软失败(质量悄悄变差);需更难的多步任务 + 多次运行才能测软失败。
- 关键区分(裁剪判据):工具结果是外部化的、作为独立 tool 消息常驻 msgList,永远在;模型思考里的「计划/中间推断」若未写进 content/tool_calls 则一抽即失。抽 reasoning_content 丢的是后者,不是工具结果。
- 上下文增长:LLM API 无状态,服务器两次请求间不记忆,每轮重发整部历史 → 一次 n 轮会话累计处理 token ≈ O(n²)。第二次请求 prompt_tokens 明显变大主因是工具结果被注入上下文。这是「上下文压缩/工具结果裁剪/跨会话 Memory」存在的根本理由。
- 错误分支是最少被执行、最少被测试的代码,最易藏「引用不存在的变量」(先后踩过 text(TDZ)、err(应为 e)两次)。
- 设计债(记一笔):callLLM 的 `!res.ok` 仍 `process.exit(1)` —— 纯「发 HTTP」的函数不该拥有退进程的权力,应把错误抛/返回给上层,由 loop 决定重试/降级/终止。阶段 2 写 loop 时删。
- 流式(SSE):`res.body` 吐字节(Uint8Array),须 TextDecoder 解码且带 `{ stream: true }`(多字节字符可能被切在 chunk 边界)。SSE 按行,但网络 chunk 边界不保证落在行边界 → 需 buffer:`+=` 后切出完整行、半行留 buffer 等下一 chunk。`data:` 前缀、`[DONE]` 结束。
- 流式 tool_calls 分片:两个 index 要分清 —— `choices[0].index`(第几个 choice,恒 0)vs `delta.tool_calls[k].index`(第几个 tool_call,才是分组键)。拼接规则:id / type / name 取第一次出现(后续片这些字段 undefined,不能覆盖),arguments 字符串片段按序 `+=`;用 index 定位而非 push(分片可能乱序到达)。坑:短参数时 GLM 一个 chunk 发完整个 tool_call,“追加”分支不触发,长参数才切片 → 短 case 测不出 bug,必须 fixture 造长/乱序分片。
- 纯逻辑 / IO 分离(harness 工程通用):拼接是纯函数(deltas→结构),网络是 IO。焊一起 → 只能靠 flaky 的真实 API 测;拆开 → 纯逻辑喂 fixture 确定性测,IO 用假 stream 单独测。「只能靠真实外部系统才能测」往往就是逻辑和 IO 焊死的信号。
- workflow vs agent:判据不是任务名字,是「输入方差 + 一条固定流程能否服务所有输入」。同一任务(如现状调研)可以是 workflow 也可以是 agent。agent 代价=轮数运行时由模型决定→不可预测→token/耗时飘、难复现。默认「能 workflow 就别 agent」,用灵活性换代价要值得。大佬把现状调研“去流程化”(只留工具+业务域地图+映射,流程交给模型)=判断输入方差大到固定流程 hold 不住 → 用 agent;哪个更好用 benchmark A/B 定。
